🔬 Technical Analysis

Mathematical analysis of BC API limits, concurrency, and theoretical throughput maximums

📊 Business Central Cloud API Rate Limits

Microsoft enforces rate limiting on BC Cloud SaaS APIs to ensure service stability and fair resource allocation. Understanding these limits is critical for designing high-throughput integrations.

Official Rate Limit Specifications

These are per-user limits that apply to each user or service principal (Entra app identity). Microsoft introduced these per-user limits in December 2023 to replace the previous per-environment limits, enabling better throughput scaling with multiple identities.

Limit Type Threshold Time Window HTTP Response
Request Rate (per user/service principal) 6,000 requests 5-minute sliding window 429 Too Many Requests
Max Concurrent Requests 5 per user Simultaneous 503 Service Unavailable
Max Connections 100 per user Simultaneous (processed + queued) 429 Too Many Requests
Operation Timeout 8 minutes Per request 408 Request Timeout

Source: Microsoft Learn - Operational Limits for Business Central Online (OData per-user limits)

⚠️ Key Insight — Two Limits, Different Constraints:
  • Rate limit (6,000 / 5 min): At most 20 requests/sec sustained. Only hit if requests complete in under ~50ms, which isn't realistic for document creation.
  • Concurrent requests (5 per user): This is the actual binding constraint in practice. With 5 in-flight requests at once, throughput = 5 / avg_response_time_sec.

Each Entra app identity gets its own independent buckets for both limits — this is why multi-app architecture scales linearly.

🧮 Theoretical Throughput Calculations

There are two concurrent limits that govern throughput. The 5 concurrent requests limit is the practical binding constraint for document creation workloads where response times are hundreds of milliseconds. The rate limit (6,000/5min) only becomes relevant when requests complete in under ~50ms.

Throughput = 5 concurrent requests / avg_response_time_seconds

At 300ms avg response: 5 / 0.3 = 16.7 docs/sec max
At 500ms avg response: 5 / 0.5 = 10 docs/sec max
At 2,300ms avg response (SO): 5 / 2.3 = 2.2 docs/sec max ← matches our SO results!

Single Entra App - Traditional API

With the traditional API pattern (separate calls for header and lines), creating a single document with 3 lines requires:

1 POST (Sales/Purchase Order Header) +
3 POST (Individual lines) =
4 API calls per document

Maximum theoretical throughput (rate-limit bound, assumes very fast requests):

Rate limit bound: (6,000 / 300s) / 4 calls = 5 docs/sec
Concurrency bound at 1,000ms avg: 5 / 1.0 / 4 calls = 1.25 docs/sec
Whichever is lower is the actual limit

Single Entra App - Deep Insert API

Deep Insert creates the header and all lines in a single API call:

1 POST (Header + 3 Lines in single payload) =
1 API call per document
75% API call reduction vs traditional

Maximum theoretical throughput (rate-limit bound):

Rate limit bound: 6,000 / 300s = 20 docs/sec
Concurrency bound at 300ms avg: 5 / 0.3 = 16.7 docs/sec
Concurrency bound at 500ms avg: 5 / 0.5 = 10 docs/sec
In practice, concurrency limit (5) is the binding constraint, not the rate limit

Multiple Entra Apps - Parallel Scaling

Since limits apply per Entra application registration, using multiple apps scales linearly — each gets its own 5 concurrent requests and 6,000 req/5min buckets:

Max_Throughput = N_apps × (5 / avg_response_time_sec)

With 2 apps at 300ms avg: 2 × 16.7 = 33 docs/sec
With 5 apps at 300ms avg: 5 × 16.7 = 83 docs/sec
With 10 apps at 300ms avg: 10 × 16.7 = 167 docs/sec
✅ Deep Insert + Multi-App Architecture is the optimal combination for maximum throughput while minimizing API consumption and staying within rate limits.

💡 Reality Check: These are theoretical limits based on the 5 concurrent requests per app, assuming full utilisation with 5 threads. Real-world throughput is also constrained by:
  • Network latency: Typically 200-500ms round-trip to BC Cloud, which directly raises response time and lowers throughput
  • BC backend processing: Document validation, business logic, database writes
  • Database constraints: Azure SQL DTU limits, locking, indexing
  • Number series contention: High concurrency can cause blocking on sequential number generation

Our deep insert PO tests achieved ~60% of the concurrency-based theoretical maximum (~9 docs/sec vs ~14 theoretical at 350ms avg), which is strong for real-world conditions. SO throughput (~2.1 docs/sec) matches the theoretical ceiling almost exactly at 2,300ms avg response time.

Our test results reveal critical insights about thread scaling:

Multi-App, 5+5 threads 10 11.77 docs/sec 1.18 docs/sec/thread

🔴 Bottleneck Identified: Doubling Sales Order threads from 5 to 10 (test #3) decreased throughput. This indicates a Sales Order processing bottleneck in BC's backend, not a rate limit issue.

Optimal Thread Configuration

Based on empirical results:

  • 5 SO threads + 5 PO threads = optimal balance
  • Purchase Orders scale better than Sales Orders under load
  • Multi-app architecture provides 13% throughput improvement over single-app
  • Beyond 10 total threads, diminishing returns occur due to BC backend constraints

💡 Optimization Strategies

1. Deep Insert Pattern (Implemented ✅)

  • Reduces API calls by 75%
  • Single atomic transaction per document
  • Lower network overhead
  • Achieved 10.38 docs/sec vs 1.53 traditional (6.8x improvement)

2. Multi-App Architecture (Implemented ✅)

  • Separate Entra apps for SO vs PO
  • Independent rate limit buckets
  • Reduced authentication contention
  • 13% throughput improvement observed

3. Thread Pool Tuning

  • Use 5 SO threads + 5 PO threads as baseline
  • Monitor for 429 responses to detect rate limiting
  • Don't exceed 10-15 total threads without additional apps
  • Consider workload ratio (SO vs PO) when distributing threads

4. Connection Pooling & Keep-Alive

  • Reuse HTTP connections to reduce TCP handshake overhead
  • Keep OAuth tokens cached (1-hour lifetime)
  • Use persistent sessions where possible

5. Batch Operations (Future)

  • OData $batch endpoint allows multiple operations in single request
  • Potential for further API call reduction
  • Not yet tested in this study

🎯 Key Takeaways

  1. Deep Insert is mandatory for high-throughput scenarios - 6.8x improvement over traditional API
  2. Rate limits are real but achievable with proper architecture (20 req/sec per app)
  3. Multi-app architecture scales linearly for extreme throughput requirements
  4. Optimal thread count is 10 (5 SO + 5 PO) - more threads = diminishing returns
  5. Backend bottlenecks (not rate limits) constrain real-world performance to ~50% of theoretical max
  6. Sustained throughput (endurance) is lower than burst capacity due to backend resource management
