🚨 Key Finding: BC Backend Contention with 15 Concurrent SO Requests

Despite using 3 separate Entra apps (each with its own 5-concurrent-request limit), throughput did not scale — it actually dropped slightly below the single-app baseline (1.94 vs 2.08 docs/sec). The root cause: response times jumped from ~2,400ms to ~7,140ms as the BC backend struggled with 15 simultaneous Sales Order creations.

The model still holds — 15 threads / 7,140ms avg = 2.10 theoretical ≈ 1.94 observed. The per-user API limits were respected, but the BC business logic layer (Sales Order creation involves complex validation, inventory checks, pricing) became the bottleneck, not the API layer.

Contrast with PO: PO at 15 threads would yield ~9×3 = 27+ docs/sec, because PO creation is ~350ms (light backend processing). SO is ~2,400ms+ because it does much more work server-side.

🔬 Test Configuration

  • Pattern: Deep Insert API (1 call per document)
  • Document Type: Sales Orders only
  • App Pool Size: 3 Entra app registrations
  • Threads per App: 5 (SO-T1–T5 → App1, T6–T10 → App2, T11–T15 → App3)
  • Total Concurrent Threads: 15
  • Lines per Document: 3 lines
  • App Version: v1.0.0.7
